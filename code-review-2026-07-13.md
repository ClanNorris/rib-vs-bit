### Message flow — full round-trip (verified, not from docs)
1. **Input:** `MainScene.handlePlayerInput()` (network branch, MainScene.js:742-771) → `network.sendMove(dir)` → `{type:'input', move}` over WS. Jump SFX plays optimistically at send time.
2. **Queue:** `server/index.js` `ws.on('message')` (index.js:148-159) → `GameRoom.queueInput()` (GameRoom.js:365-370), gated by `_inputsOpen`.
3. **Simulate:** `GameRoom._tick()` every 50ms (GameRoom.js:428-467): `_updatePlayerStates` → `_updateLanes` → `_processInputs` (red queue fully drained, then blue) → `_applyPlatformCarry` → `_checkHazards` → `_checkScoring`.
4. **Broadcast:** `_broadcastTick()` (GameRoom.js:831-856) sends the complete snapshot (players, all platform/vehicle x-positions, pad states) to both clients, 20×/sec.
5. **Render:** `network._dispatch` → `MainScene._applyServerTick()` (MainScene.js:904-971) snaps sprite positions directly — no interpolation, no prediction. Events (`playerDeath`, `score`, `tongueFired`, `tongueHit`, `gameOver`) arrive as separate typed messages driving local audio/visuals.

### Pre-registered verification #1: does the "server-authoritative" gate actually hold?
**Yes — while connected.** `MainScene.update()` (MainScene.js:698-705) runs only `laneSystem.updateDecorations()` when `this.localPlayerId` is set, and the local carry/collision/scoring block (MainScene.js:720-734) is wrapped in `if (!this.localPlayerId)`. `handlePlayerInput` (MainScene.js:742) likewise sends inputs instead of simulating. The doc's claim is accurate **but the gate variable is fragile**: it is keyed on `localPlayerId`, which `onDisconnected` nulls — see finding C-1, the most serious issue in this review.

## Findings

### [Critical] [NEW] — Socket drop mid-match silently reactivates local simulation ("zombie match")
- **Location:** `MainScene.js` — `onDisconnected` callback (line 351-354: `this.localPlayerId = null`); `update()` network gates (lines 699, 720: `if (this.localPlayerId)` / `if (!this.localPlayerId)`); `handlePlayerInput()` local branch (lines 773-800).
- **Issue:** The only thing distinguishing "online match" from "local same-keyboard match" at runtime is the truthiness of `localPlayerId`. When the WebSocket closes for any reason (server crash, Railway restart, network blip), `onDisconnected` sets it to `null` — and on the very next frame `update()` takes the local-sim branch: `laneSystem.update(dt)` moves hazards locally, `collision.checkPlayerHazards` kills frogs locally, `scoring.checkLilyPadCapture` awards points locally, and `handlePlayerInput` gives the one remaining keyboard control of **both** frogs (red via WASD, blue via arrows). The only disconnect signal is `console.log('[net] disconnected')`.
- **Why it matters:** A Railway crash or deploy mid-match doesn't end matches — it turns every live match into a nonsensical offline game where the board keeps moving, the opponent's frog is a piñata, and local scoring can even "win" the match. Players will experience this as the game going insane, not as a disconnect. This is guaranteed to happen at public scale (every server deploy does it).
- **Recommendation:** In `onDisconnected`, do **not** null `localPlayerId` (or add a separate `wasNetworkMatch` flag that stays true). Freeze the game (`roundGate.setGameOver()` or a new `disconnected` phase), and show a "Connection lost — refresh to play again" overlay via `uiOverlay` (the `showAbandoned` screen is 90% of what's needed). Nulling the mode flag should never be the disconnect handler's job.

### [High] [NEW] — Mid-match reconnect is half-built and lands the returning player in a frozen, mismatched world
- **Location:** `server/GameRoom.js` `addClient()` (lines 244-278 — `_initGame()` only fires when `phase === 'waiting' || phase === 'gameOver'`); `src/systems/network.js` `connect()`/`onclose` (lines 69-91 — no auto-reconnect); `MainScene.js` `onCountdown` (line 262 — intro only fires on `value === 3`), `_applyServerTick` (line 904 — applied unconditionally regardless of client phase).
- **Issue:** The server has a real 30s forfeit window (`_startReconnectWindow`, GameRoom.js:329-352) and cancels it when the player's slot refills (`addClient`, lines 246-252). But the client has **no reconnect logic at all** — the only way back within 30s is a manual page refresh. That fresh page: shows the title screen, connects on click, receives `joined`… and nothing else. Because the room phase is `live`, `addClient` never re-sends `gameStart` (no lane plan), never sends `countdown`. The returning client keeps its own independently-randomized lane plan (from `create()`'s local `createMatchLanePlan()`), its `roundGate` stays in `menu` (input permanently disabled, `isInputEnabled()` false), decorations never sync (`isWorldRunning()` false in menu), yet `_applyServerTick` still snaps frog and hitbox positions from a server world with different platform sizes/templates. Meanwhile the forfeit timer was canceled, so the match no longer resolves on its own.
- **Why it matters:** The reconnect feature, as shipped, converts a recoverable disconnect into a *worse* outcome than no feature: the survivor now faces a permanently frozen opponent with no forfeit countdown (the survivor can still farm pads to 3, but nothing communicates that), and the returner stares at an uncontrollable, visually garbled board. This will be the single most common failure players actually hit (mobile tab switching, flaky Wi-Fi).
- **Verdict on the pre-registered expectation:** the expected answer ("socket drop = silent match death, room may leak") is **wrong in both directions**. There is substantial disconnect handling: one-drop → 30s forfeit window with countdown (`removeClient` → `_startReconnectWindow`); both-drop → tick pause (`removeClient`, GameRoom.js:307-314) + eventual cleanup. Rooms do not leak permanently — but note the both-drop path is scrappier than it looks: `startEmptyRoomGrace`'s interval self-cancels on its first tick when `phase !== 'gameOver'` (index.js:58-61), so a mid-match double-drop is actually cleaned up by the 60-second orphan sweep (index.js:177-184), not by the grace window. Bounded, but by the belt-and-suspenders path, not the designed one.
- **Recommendation:** Pick one and ship it: **(a)** honest minimal — on rejoin into a `live` room, have the server end the match (`_endGame(survivorId)`) or send the existing `gameover`-abandoned message so both clients reach a clean screen; or **(b)** real resume — on rejoin into `live`, re-send `gameStart` with the *current* lane plan plus a state snapshot, and add a client `resync` path that rebuilds the world and jumps `roundGate` to `live`. Option (a) is a few lines and removes the trap; (b) can come later. Either way, add client-side auto-reconnect (retry `connect()` with backoff for ~25s) so the 30s server window is actually reachable without a manual refresh.

### [High] [NEW] — No heartbeat/ping-pong: zombie connections hold slots and block rooms
- **Location:** `server/index.js` — `wss.on('connection')` (line 89, no `ws.ping()`/`pong` tracking anywhere); `isStaleSocket()` (lines 36-38 — only treats `readyState !== OPEN` as stale); `GameRoom._isSlotLive()` (GameRoom.js:239-242 — same OPEN check); orphan sweep (index.js:177-184 — skips rooms with any non-null client).
- **Issue:** A client that vanishes without a TCP FIN (phone loses signal, laptop lid closes, NAT timeout) leaves a socket whose `readyState` is still `OPEN` for however long the OS takes to notice — minutes to indefinitely behind some proxies. Every liveness check in the codebase equates OPEN with alive. Consequences: (1) the dead player's slot reads as occupied, so their own reconnect attempt is rejected with "Room is full" (index.js:137-141) — `isStaleSocket` can't help because the zombie is OPEN; (2) the opponent never gets the 30s forfeit window because `close` never fired; (3) a room whose only occupant is a zombie is never swept, leaking it permanently; (4) `broadcast` keeps serializing 20 ticks/sec into the zombie's send buffer.
- **Why it matters:** Friends & Family testing on stable home Wi-Fi never exercises half-open sockets. Public mobile traffic exercises them constantly. "Room is full" against your own dead ghost is an unfixable-by-the-user lockout of that room code.
- **Recommendation:** Standard `ws` heartbeat: on connection set `ws.isAlive = true`, `ws.on('pong', () => ws.isAlive = true)`; a 30s interval does `if (!ws.isAlive) return ws.terminate(); ws.isAlive = false; ws.ping();`. `terminate()` fires the existing `close` handler, so the forfeit window, slot clearing, and sweep all start working for free. ~15 lines in `index.js`.

### [High] [NEW] — No resource limits anywhere: unbounded rooms, connections, and message sizes
- **Location:** `server/index.js` — `new WebSocketServer({ port: PORT })` (line 14 — no `maxPayload`); room creation (lines 110-122 — any `?room=` string of any length creates a `GameRoom`); no per-IP connection cap; `GameRoom.queueInput()` (GameRoom.js:365-370 — unbounded push; note `_inputsOpen` remains `true` after `gameOver` since it is only reset in `_startCountdown`, so a client idling on the game-over screen can grow the queue until the ~20s grace teardown).
- **Issue:** A single misbehaving or malicious client can: open thousands of connections, each minting a `GameRoom` (with a 200-player-state object graph) keyed by an arbitrarily long room string; send megabyte messages (ws default `maxPayload` is 100 MiB — each one is `JSON.parse`d in the message handler at index.js:150); or pump input messages far faster than the 20 Hz drain. Nothing rate-limits, nothing caps, nothing validates room-ID shape.
- **Why it matters:** On Railway's small instances this is a one-laptop denial of service against every live match, and even *accidental* abuse (a stuck key autorepeating `sendMove`, a link crawler hitting `?room=` URLs) consumes real resources. This is exactly the "nobody has tried to break it yet" category the review brief flags.
- **Recommendation:** Proportionate hardening, all in `index.js`: (1) `new WebSocketServer({ port: PORT, maxPayload: 1024 })` — no legitimate message exceeds a few hundred bytes; (2) validate room IDs: `/^[a-z0-9]{1,12}$/i` or reject (client generates 6-char lowercase alphanumerics via `generateRoomId`, network.js:211-216); (3) cap total rooms (e.g. 500) and reject creation beyond it; (4) a trivial per-socket token bucket (e.g. 30 msgs/sec, `ws.terminate()` on breach); (5) in `queueInput`, drop inputs when `queue.length > 8` — humans can't exceed that between 50ms ticks.

### [Medium] [NEW] — No Origin check on the WebSocket server
- **Location:** `server/index.js` `wss.on('connection', (ws, req))` (line 89) — `req.headers.origin` is never read; no `verifyClient`/`handleUpgrade` filtering.
- **Issue:** Browsers do not enforce same-origin policy on WebSocket connections; the server is the only place an origin allowlist can live, and there isn't one. Any web page or headless script can connect to the Railway endpoint, join/occupy rooms, and drive inputs.
- **Why it matters:** Combined with guessable 6-char room codes and the "first connection takes the red slot" rule, a trivial off-site bot can squat rooms or third-wheel into matches ("Room is full" for the real second player). No secrets are at risk — this is griefing/resource surface, not data exposure — hence Medium.
- **Recommendation:** In the connection handler: `const origin = req.headers.origin; if (origin !== 'https://rib-vs-bit.netlify.app' && !origin?.startsWith('http://localhost')) { ws.close(1008, 'bad origin'); return; }`. Keep the localhost allowance for the Vite dev proxy (which sets `rewriteWsOrigin: true` in `vite.config.js`, so decide the dev-origin value deliberately). Note this stops casual browsers, not custom scripts that forge the header — pair with the rate limits above.

### [Medium] [NEW] — `restart` message bypasses the ready-ready handshake (and the client never sends it)
- **Location:** `server/index.js` message handler (lines 154-155: `msg.type === 'restart'` → `room.handleRestart()`); `GameRoom.handleRestart()` (lines 804-816 — no check of `_readyStates`); intended path is `handleReady()` (lines 819-827); client `sendRestart()` (network.js:175-177) is exported but never called; `onRestart` (MainScene.js:317-319) obeys unconditionally with `scene.restart()`.
- **Issue:** The rematch flow is designed as a mutual ready-check (`handleReady` requires both flags). But any client can send a raw `{type:'restart'}` at `gameOver` and `handleRestart` fires immediately, broadcasting `restart` and yanking the opponent's client into `scene.restart()` without their consent.
- **Why it matters:** A one-line message from a modified client forces the opponent into a rematch loop they can't decline — mild griefing today, but also a correctness landmine: it clears both slots (`this.clients = {red:null, blue:null}`) while a real player may still be deciding, putting the room into the reconnect-race machinery for no reason.
- **Recommendation:** Delete the `msg.type === 'restart'` branch from `index.js` (the legitimate path is `ready`), and remove the dead `sendRestart` from `network.js`. `handleRestart` stays as the internal function `handleReady` calls.

### [Medium] [NEW] — Client runs its own player state machine against the server's authoritative one
- **Location:** Client: `playerState.update()` called every frame from `MainScene.update()` (line 687), `beginRespawn` → `resetPlayerVisualState` snaps the sprite to spawn (playerState.js:67-84, 86-104); `playerDeath.beginPlayerDeath` runs a 400ms position/alpha tween (playerDeath.js:20-31, 42-53). Server: `_applyServerTick` overwrites `player.state` and `sprite.x/y` every 50ms (MainScene.js:910, 933-936); server keeps the corpse at the death position for `RESPAWN_DELAY_MS` (400ms) before `_resetPlayer` (GameRoom.js:506-517, 735-740).
- **Issue:** Two independent state machines write the same fields on different clocks. Concretely: on `playerDeath`, the client's river-death tween animates `sprite.y` downward while every tick snaps it back (y-fight jitter); when the client's respawn timer fires it teleports the sprite to spawn, then the next tick drags it *back to the death tile* until the server's own 400ms respawn elapses; the client's INVULNERABLE→ALIVE timing (`respawnInvulnMs` from `scene.time.now`) drifts from the server's (`aliveAt` from `Date.now()`), so `player.state` flip-flops between writes.
- **Why it matters:** Today the damage is visual (corpse teleport-flicker on every death — visible in normal play) — but any future logic that reads `player.state` client-side (input gating, effects) inherits a value that alternates between two sources several times per second. This is the "duplicated logic that could drift" the review was asked to find, live and observable.
- **Recommendation:** In network mode, make the server the sole writer of `state`/position: have `onPlayerDeath` play *effects only* (splash, tint, camera) without `requestPlayerDeath`'s position tween-and-respawn, and skip `playerState.update()` when `localPlayerId` is set. The DYING tween can still run purely on alpha/angle (fields the server never writes) if the fade is wanted.

### [Medium] [KNOWN/ACCEPTED] — Game data is hand-copied in three places with no consistency enforcement
- **Location:** Lane defs + tuning constants exist independently in `server/constants.js` (RIVER_LANE_DEFS/ROAD_LANE_DEFS/SPEED_VARIANCE, lines 71-120), `src/config/lanes.js` (lines 3-111), and `src/config/gameTuning.js` (laneSpeedVariance, lines 31-59). Simulation *logic* is likewise mirrored: `GameRoom._findPlatformUnder`/`_applyPlatformCarry`/`_checkHazards`/`_tryMove` vs `platformSupport.js`/`movement.js`/`collision.js`.
- **Issue:** Every balance change requires manually editing 2-3 files in lockstep; a missed mirror produces silent client/server divergence (mispredicted tongue draws, platforms rendered at wrong widths). `rib-vs-bit-status.md` ("Architectural gap, still unresolved", Backlog) documents this and records that the July 8 session hit it repeatedly.
- **Why it matters:** Wrong values here don't crash — they desync, the worst failure mode this architecture has.
- **Recommendation:** A single `shared/` module consumed by both sides. The server is CommonJS and the client ESM, but a plain JSON file (`shared/gameData.json`) imported by both (Node `require`, Vite JSON import) needs zero build changes. The mirrored *logic* is harder to unify (Phaser objects vs plain state) and can stay duplicated — but the *data* should not be.
- **Challenge the acceptance?** **Yes.** As a deferred cleanup it was defensible; with two forks planned it no longer is. Super Turbo is precisely a "change the lane defs and tuning" fork — forking now triples-per-fork the copy burden and every fork inherits the desync trap. This is the cheapest high-leverage refactor on the board and should precede both forks.

### [Medium] [NEW] — `server/node_modules` and three zip snapshots are committed to the repo
- **Location:** `.gitignore` line 1 (`/node_modules` — root-anchored, does not match `server/node_modules`); `git ls-files` shows `server/node_modules/ws/**` (22 files) plus `rib-vs-bit-phaser-debug.zip`, `rib-vs-bit-pre-online.zip`, `rib-vs-bit-tongue-debug.zip` tracked.
- **Issue:** A vendored dependency that silently drifts from `server/package-lock.json` (a `npm update` in `server/` changes files git now wants to commit), and three opaque archives of old code states that git history already provides.
- **Why it matters:** Beyond bloat, the vendored `ws` can mask a mismatch between what runs locally and what Railway installs from the lockfile at deploy — the two can be different versions and nobody would notice.
- **Recommendation:** Change `.gitignore` line 1 to `node_modules/` (unanchored), `git rm -r --cached server/node_modules`, and `git rm --cached *.zip` (add `*.zip` to `.gitignore` if the local copies are wanted).

### [Medium] [KNOWN/ACCEPTED] — Zero automated test coverage
- **Location:** `package.json` `"test": "echo \"Error: no test specified\" && exit 1"`; no test files anywhere. CLAUDE.md documents this as fact ("No test runner is configured").
- **Issue / highest-risk areas ranked by blast radius:** (1) **`GameRoom` tick pipeline** (`_processInputs`, `_tryTongue`, `_tryMove`, `_checkHazards`, `_checkScoring`) — pure logic on plain objects, zero Phaser dependency, and every bug here hits both players in every match; trivially unit-testable by constructing a room and calling `_tick` with faked `Date.now`. (2) **Room/connection lifecycle** (`addClient`/`removeClient`/`handleRestart`/`isStaleSocket` + the grace/forfeit timers) — where this review found its worst bugs; testable with stub sockets (`{readyState:1, send(){}}`). (3) **Client/server constant parity** — one test asserting `server/constants.js` values equal `src/config` values catches the desync class of finding M-KNOWN above until the shared module exists. (4) **`_applyServerTick` + `serverPosLocked` release** (MainScene.js:913-925) — the one piece of client prediction, with three release paths that must all fire. (5) **`getMatchStateCallout`** — already contains a wrong-winner bug (see L-1).
- **Recommendation:** `npm i -D vitest` (already Vite-native), start with (1) and (2) — perhaps 20 tests. Do not attempt Phaser-scene testing; it's poor ROI here.
- **Challenge the acceptance?** **Yes, narrowly.** Skipping UI tests is the right call; skipping tests on an 880-line authoritative server whose bugs desync paying-attention players is not, especially with two forks about to diverge this exact code.

### [Low] [NEW] — Simultaneous events resolve with a fixed red-player bias
- **Location:** `GameRoom._processInputs` (line 527: `for (const id of ['red','blue'])` — red's whole queue drains first, so red's tongue/move preempts blue's same-tick input); `_checkScoring` (lines 750-763 — red's pads checked first with an early `return` on capture).
- **Issue:** Two inputs landing in the same 50ms tick have a defined, deterministic resolution order — always red first. The sharpest case: both players reach their final pad on the same tick at 2-2 — red's capture is processed, `_capturePad` fires `_endGame('red')`, blue's capture is never evaluated. Same-tick mutual tongue fires: red's pull relocates blue before blue's queued input processes.
- **Why it matters:** Deterministic is good (no divergence); *biased* is the problem — over many matches red holds a small structural edge in every same-tick contest, and a 2-2 photo finish always crowns red. Rare per-match, guaranteed at scale.
- **Recommendation:** Alternate drain order by tick parity (`tickCount % 2 ? ['red','blue'] : ['blue','red']`) and, in `_checkScoring`, collect both candidate captures before applying — if both captured on the same tick at match point, apply both and let a genuine tie-break rule decide (or simply also alternate the check order).

### [Low] [NEW] — `getMatchStateCallout` announces "WINNER! RIB!" when blue wins
- **Location:** `src/systems/matchState.js` lines 11-12: `if (redWins) return 'WINNER! RIB!'; if (blueWins) return 'WINNER! RIB!';` — copy-paste error, the second should be `'WINNER! BIT!'`.
- **Issue:** Currently unreachable — winning captures route through `scoring.capturePad`'s `onWin` path (scoring.js:77-80), never `onRegularPoint` → `getMatchStateCallout`, and network mode bypasses this file entirely — but the function's contract says it handles win states, and it handles one of them wrongly.
- **Why it matters:** The next person to call this helper "because it already handles wins" ships a wrong-winner banner for half of all matches.
- **Recommendation:** One-character-class fix: return `'WINNER! BIT!'`. (Or delete both branches with a comment that win announcements live in `endGame`.)

### [Low] [NEW] — Rematch reconnect race can silently swap the players' colors/sides
- **Location:** `GameRoom.handleRestart()` (lines 804-816 — `this.clients = {red:null, blue:null}` synchronously); `server/index.js` slot assignment (lines 130-142 — first arrival takes red, second takes blue, with no memory of prior identity).
- **Issue:** After a rematch both clients `scene.restart()` → reconnect. Whichever socket wins the race gets `red`. The player who was Bit last match may now be Rib — different color, opposite side of the board, different pads to attack.
- **Why it matters:** Not unfair (the game is symmetric) but disorienting: "why am I suddenly the red frog at the bottom?" reads as a bug to players, and it's nondeterministic — most rematches won't swap, then one will.
- **Recommendation:** Pass the previous identity on reconnect (`?room=X&prefer=blue` from the client, honored when that slot is free), or have the server remember socket→playerId by a short-lived token issued in `joined`.

### [Low] [NEW] — Optimistic client feedback fires on inputs the server rejects
- **Location:** `MainScene.handlePlayerInput` network branch (line 768: `playJump()` at send time; the cooldown check at line 754 mirrors the server's, but stun — `stunUntil`, enforced server-side at GameRoom.js:544 — is not mirrored, and edge-clamped moves are not predicted); touch path `netOpts.onMove` (line 660: `sendMove` + `playJump` with **no** client-side cooldown at all — `touchControls` hitZone fires per tap, touchControls.js:52-65); moves sent during server `scorePause` are queued then discarded by `_startCountdown` (GameRoom.js:404-406) while the client still plays the jump sound.
- **Issue:** The jump SFX asserts "you moved" for inputs the server may drop (stunned, board edge, score pause, cooldown-on-touch). The frog doesn't move; the sound says it did.
- **Why it matters:** During the 1s stun after a tongue hit — the exact moment players mash keys — every press plays a jump sound over a stationary frog. It reads as broken input, which is worse than honest silence.
- **Recommendation:** Cheapest: mirror `stunUntil` client-side (it already arrives in every tick's `_serializePlayer`, GameRoom.js:858-865) and gate both the send and the SFX on it; add the same `moveCooldown` check to the touch path. Cleaner long-term: move the hop SFX to the server-confirmed `movedThisTick` signal for the local player too (it's already used for the opponent, MainScene.js:929-931).

### [Low] [NEW] — Debug logging and dead code shipping to production

### [Note] [NEW] — No latency compensation at all: input feel degrades linearly with ping
- **Location:** `_applyServerTick` (MainScene.js:904-971) — direct assignment, both players; local moves are *not* applied locally (`handlePlayerInput` network branch only sends); the sole exception is the tongue-pull prediction (`applyTongueHit` + `serverPosLocked`, abilities.js:80-144).
- **Assessment (verifying the docs' claim):** confirmed — pure server-snap, no interpolation, no movement prediction. On LAN/regional play (<60ms RTT) a hop responds within ~2-3 ticks and the 50ms snap cadence matches the game's chunky tile aesthetic — this is a defensible design, not an oversight. At 100-150ms RTT (cross-country, mobile), every hop lags perceptibly behind the keypress and platform drift becomes visibly steppy. The `serverPosLocked` mechanism proves the team already knows how to do targeted prediction.
- **Recommendation:** Not launch-blocking. The highest-value increment later is *local move prediction only* (apply the move immediately, reconcile via the existing tick snap — the `movedThisTick`/`serverPosLocked` machinery is most of the pattern). Skip opponent interpolation; the snap aesthetic covers it.

### [Note] [NEW] — Observability: a Railway crash is diagnosable only via Railway's stdout capture
- **Location:** Logging is `console.log`/`console.error` throughout `server/index.js`/`GameRoom.js`; no `process.on('uncaughtException'/'unhandledRejection')` handlers; no health/liveness endpoint (the process serves only WS upgrades); no match/room metrics.
- **What happens today if the server crashes mid-match:** the process dies → Railway restarts it (default behavior) with an **empty `rooms` map** — all match state is in-process and unrecoverable. Every client gets `onclose` → `onDisconnected` → finding C-1's zombie local mode, with no user-facing message. Post-mortem evidence is whatever stdout Railway retained.
- **Recommendation:** (1) Add `process.on('uncaughtException', (e) => { console.error('[fatal]', e); process.exit(1); })` and the `unhandledRejection` twin so crashes log before dying; (2) attach a trivial HTTP server (`http.createServer` sharing the port via `WebSocketServer({ server })`) answering `/health` with room/connection counts — enables Railway health checks and a free uptime monitor; (3) log room create/destroy with counts (already partly there) so capacity trends are visible. All fits in ~30 lines; skip external APM.

### [Note] [NEW] — Tick payload is unoptimized but comfortably affordable
- **Location:** `_broadcastTick` (GameRoom.js:831-856) — resends static pad definitions (id/col/row) and all object ids every tick.
- **Assessment:** ~1-2 KB JSON × 20/sec × 2 clients ≈ 50-80 KB/s per match; one `JSON.stringify` per tick (single-stringify in `broadcast`, GameRoom.js:873-877 — good). One `setInterval` per room; CPU and bandwidth scale linearly with concurrent matches; dozens of matches is trivial for a small Railway instance. The procedural-assets decision holds up well: the entire client payload is Phaser + ~50KB of game code, no asset pipeline, instant load.
- **Recommendation:** Nothing now. If bandwidth ever matters: send pads only on change and drop per-tick ids (index-match, which `_applyServerTick` already relies on anyway).

### [Note] [NEW] — Security posture is otherwise sound; no XSS or secret exposure found
- **Verified:** All game-state authority is server-side — the client sends only `input`/`ready`/`restart` intents; score, position, win state are never accepted from clients (see `_processInputs`, `_capturePad`, `_endGame`). The scoped history scan (`git log --all --full-history -p -- '*.env*' '*config*' '*.json'` + working-tree credential grep) found nothing: no `.env` ever committed, `.gitignore` covers it, `VITE_WS_URL` correctly treated as public. ## Forkability Assessment (Dimension 5, both forks)

**"Super Turbo" (gameplay fork):** Client-side, gameplay data is genuinely well-factored — `gameTuning.js`, `lanes.js`, `theme.js` are clean single-purpose config, and the systems pattern means new mechanics slot in as factories. The blocker is the server: every rule that matters at runtime (speeds, cooldowns, lane defs, scoring, win condition) lives *again* in `server/constants.js` + `GameRoom.js` logic. Forking gameplay as-is means forking the server and maintaining four copies of the data (two per fork). **Verdict: do the shared-data-module refactor (Medium/KNOWN finding) first; after that, Super Turbo is mostly a config-and-content fork. The network layer itself (message protocol, room lifecycle) is game-agnostic enough to share unchanged.**

**Discord Activities port:** The seams are better than typical for a project this age:
- *WS URL resolution* — excellently localized: one function, `_connectNetwork()` (MainScene.js:896-902), plus `resolveRoomId()` (network.js:224-233). Discord's `/.proxy/` URL-mapping rewrite touches ~10 lines. Two stragglers: `onAbandoned`'s `window.location.href = window.location.origin` redirect (MainScene.js:346) and the share-link `roomUrl` (MainScene.js:357) both assume a top-level browsing context and need iframe-safe replacements.
- *Canvas sizing* — `main.js` literals + `Phaser.Scale.FIT` and the `isMobile()` branch. Discord needs container-driven resize; the FIT scaler does most of the work but the mobile/desktop fork and the fixed 1031 must become dynamic. Moderate, contained to `main.js` + `touchControls` positioning (which reads `scene.scale`, so it follows).
- *Auth handshake insertion* — the connect flow is already gated behind a user action (`showTitleScreen onStart` → `_connectNetwork`, MainScene.js:396-405), so an async OAuth step slots in front of `_connectNetwork()` cleanly. The invasive part is server-side: there is **no identity concept at all** — slots are first-come-first-served off the raw connection (index.js:130-142). Discord wants "this socket is user X in guild-channel Y" → room derivation from channel rather than `?room=`, and a token check at upgrade time. That's new code in `index.js`'s connection handler, not a rewrite of `GameRoom` — the room class itself never inspects identity beyond `'red'/'blue'`, which is the right shape for this port.

## Top 5 Priorities Before Public Launch

1. **Fix the disconnect → zombie-local-sim path (Critical, NEW).** On `onDisconnected`, freeze the game and show a "connection lost" screen instead of nulling `localPlayerId`. Until this is fixed, every Railway deploy or crash corrupts every live match into a nonsense state with zero user messaging. Smallest fix with the largest player-facing payoff in this review.
2. **Close the mid-match reconnect trap (High, NEW).** Minimum viable: server ends/abandons the match when a client rejoins a `live` room, instead of half-resuming into a frozen, mismatched client. Add client auto-reconnect so the existing 30s forfeit window is reachable at all. Mobile players will hit this path constantly.
3. **WS server hardening bundle (High ×2 + Medium, NEW).** Heartbeat ping/pong with `terminate()` on missed pong; `maxPayload: 1024`; room-ID shape validation + room cap; per-socket message rate limit; Origin allowlist for the Netlify domain. All of it fits in ~60 lines of `index.js` and is the difference between "nobody tried to break it" and "someone tried and couldn't."
4. **Single-source the shared game data (Medium, KNOWN — acceptance formally challenged).** Extract lane defs + tuning constants into one shared JSON/module before either fork exists. Both planned forks multiply the current three copies; this is the cheapest moment it will ever be.
5. **Seed the test suite on the server core (Medium, KNOWN — acceptance formally challenged).** Vitest over `GameRoom`'s tick pipeline and the room lifecycle (both plain-JS, no Phaser). These two areas produced every Critical/High finding above; ~20 tests would have caught several of them and will guard the fork divergence.

## What's Actually Solid

- **The authority model is genuinely correct.** Score, movement, collision, tongue resolution, and win state are all computed server-side; the client sends only intents. No client-supplied game state is trusted anywhere (`_processInputs`, `_tryTongue`, `_capturePad`). Many indie multiplayer projects get this wrong; this one didn't.
- **The client-side network/local gate holds as documented.** The pre-registered verification passed: `MainScene.update()` really does disable `laneSystem`, collision, carry, and scoring in network mode. The Critical finding is about the gate's *key* being fragile, not the gate being absent.
- **The systems-factory pattern is disciplined and consistent.** Every system is `createX(scene, options)` with callback wiring, a `destroyed` flag, and a `destroy()` called from a thorough `handleSceneShutdown()` (with double-fire guard). Tween/object tracking via the `track()`/`managedObjects` idiom appears in every visual system — `scene.restart()` rematches don't leak, which is the classic Phaser failure mode and it's been handled properly.
- **Race conditions around reconnect/rematch show real thought.** `isStaleSocket` eviction, `_destroyed` guards against resurrected rooms, synchronous slot-clearing in `handleRestart` to beat the close-event race, phase-checked grace timers — the sequencing comments in `index.js`/`GameRoom.js` document *why*, not just *what*. The gaps found (zombie OPEN sockets, live-phase rejoin) are at the edges of a design that got the middle right.
- **Server-resolves-and-broadcasts for shared randomness** (`materializeLane`/`rollVehicleSkins` → `vehicleSkins` in the lane-plan broadcast) is exactly the right pattern and is documented as the template for future variants.
- **The tongue-hit prediction (`serverPosLocked`/`expectedPullCol`) is a well-executed piece of targeted client prediction** — locked to server-derived values, with three explicit release paths. It proves the harder latency work is within reach when it's wanted.
- **Zero-asset procedural rendering and synthesized audio hold up.** Instant load, no pipeline, no CDN concerns; the Phaser-AudioContext-reuse rule (mobile unlock) is respected everywhere.
- **Docs are unusually honest.** CLAUDE.md and `rib-vs-bit-status.md` accurately describe the code (this review confirmed the tick model, the gate, the vestigial local mode, and the known deferrals against source), and known issues are recorded as known rather than forgotten. The doc drift this review hunted for mostly wasn't there.
